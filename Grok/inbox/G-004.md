### Task 1: one question per family, with sub-points (defects section 3(f))

Today `_questions` (`review.py`, about lines 96 to 218) makes one question for each finding and for each flagged
device. `review_page` (about lines 612 to 680) puts the questions of a system in one card. The first run of 26-0544
gave 29 questions on 11 cards, and 7 questions on one card. Two of them asked the same thing.

The form of the new page:

- Keep one card for each system. Inside a card, group the questions by family.
- A group has one heading. The heading names the family and says what to check, in plain words. Example: "Air
  Handling Unit: 7 points to check". Do not show an invented code (such as q12) in the heading.
- Each question that was a separate question before is now a sub-point of its group. A sub-point keeps its own title,
  its own notes, its own count and sources, and its own Accept, Change and (where it has one today) Delete buttons.
- Decisions do not change. They are keyed by device id, family name and finding rule, as now. `decisions.json` does
  not change. Each sub-point keeps its own `qdata` with its own ids.
- Keep each sub-point as one `.q` element, so that `_SCRIPT_PAGE` works as it does now. Put the group heading and the
  `.q` elements in one wrapper element. Change the script only if a test needs it.

Which questions go in which group:

- A question with level "family" goes in the group of its family.
- A device question or a system question goes in the group of the family of its system when the system has one
  family. When the system has more than one family, it goes in one group that is named after the system.
- Merge duplicates. A finding on one device can name a second device of the same system in its words (the id of the
  second device, as a whole token in `what` or `fix`). When the second device has its own flag, do not make a
  separate sub-point for it. Put the words of its flag in a note on the sub-point of the finding. That sub-point
  keeps the device id of the finding. (Defects section 3(f): the finding on d22 that names d23, and the flag on d23.)
  Match ids only. If the findings name devices in another way, write a question. Do not guess.
- The line "N of M question(s) shown" and `MAX_QUESTIONS` count a group as one question. The rank of a group is the
  lowest rank of its sub-points. "Answered" counts the sub-points that have an answer, as now. "Show all questions"
  works for groups as it does now.

Tests (the helpers `_page` and `_find` in `tests/bms/test_review.py` are a pattern):

- A system with one family and 7 flagged devices or findings (invented) gives one card for that system. The card has
  one group heading and 7 sub-points. Each sub-point has an Accept button and a Change button, and its own `qdata`
  with its own device id.
- Three flagged devices in one family give one group with three sub-points. A decision on one sub-point changes only
  that device. Check it with `review.apply_decisions`.
- A finding on device A that names device B in its words, and a flag on B, give one sub-point for A. The words of the
  flag of B are in its notes. There is no sub-point for B.
- A system with two families: each family count question is in the group of its family. The other questions are in one
  group that is named after the system.
- A group counts as one question in the line "N of M question(s) shown".
- Many existing tests in `tests/bms/test_review*.py` and `tests/bms/test_t005b_review_once.py` count cards or `.q`
  blocks, or read titles. Change the expected result of each one that this task changes on purpose. List each in the

### Task 3: a system with no devices and a reason (defects section 3(c))

Today a system with no devices prints no block. `_system_blocks` (about line 1056) writes its `left_out_text` to the
Evidence Package only. The proposal says nothing. Example: a coil bank whose valves are in the block of an ERV. The
writer gave the system a `no_scope_reason`.

New rule. When a system has no devices, has a `no_scope_reason` that is not blank, and has no named exception lines
(`exceptions` is empty), the proposal prints one short note:

- Case A. The reason names a block that carries the devices. Print one "*" line in that block, after its other "*"
  lines. The text is the reason in the writer's words. When the reason does not hold the name of the system, put the
  name first: "*Coil Bank: <reason>".
  A reason names a block when it holds, as whole words and in any case, the `key`, the `name` or a family tag of
  exactly one other system of the base bid that has devices. Example: the reason "The coil valves are counted with
  ERV-1." names the ERV system that has the family tag ERV-1.
- Case B. The reason names no block, or more than one. Print one line "No BMS scope: <reason>" at the end of the scope
  section. It is one `Item` of kind "note". Put it as the last item of the last block of the base bid, before the
  Demolition Scope block. If you find a better place that needs no file outside the list above, use it and say so in
  the report. If the job has no block, keep today's behaviour.
- A system that has named exception lines keeps today's behaviour. Its EXCEPTION lines print. It gets no note. Do not
  print an EXCEPTION line for any other system (`rules.md`, "Named exceptions", about line 588).
- A system with no `no_scope_reason` keeps today's behaviour. So does a system of an alternate that has no devices.
- The Evidence Package keeps its left-out note (`left_out_text`). The new note is also in `draft.lines` (`_traced`), so
  the Evidence Package shows it.
- Find the carrying block before the system loop of `render` runs, because the block can come before or after the
  system in the print order.
- The words "No BMS scope:" are a constant in `render.py`, next to `LEFT_OUT`. Do not edit the Playbook.
- When the reason is longer than 150 characters, pass the text through `short_points`, as `_notes` does. HarkPro's
  T-008 changes that function. Do not edit it.
