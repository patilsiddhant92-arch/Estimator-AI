## 1. What this is

A tool that reads an HVAC/BMS controls bid package — mechanical drawings, specs,
control diagrams, addenda, RFIs, exhibits — and produces two deliverables an AME
estimator can issue after a short, structured review:

1. **Proposal** (`.docx`) — the client-facing scope of work
2. **Price Sheet** (`.xlsx`) — the same scope, priced

Plus a third artifact that is not optional, and is the reason the first two can be
trusted:

3. **Evidence Package** (`.xlsx`) — every quantity's provenance, every flag, every
   discrepancy, every assumption, every revision change

It counts **equipment** and it counts **devices** — sensors, thermostats, damper
actuators, controllers. Devices are not a secondary concern to be handed elsewhere:
without them there is no scope, and they are the part the schedules do not give you.

### Core value

**A scope you can defend, line by line.** If a number in the proposal cannot be
traced to a sheet, a spec paragraph, or a named assumption, the tool has failed —
regardless of whether the number happens to be right.

### Success criterion

The estimator's job changes from *writing the scope* to *resolving a short list of
flagged decisions*. The measure is the length of that list and the rate at which its
defaults are accepted, tracked against the reference corpus (§6).

## 3. Naming

The existing shorthand — `R36`, `FE`, `Package D`, `GEMS`, `G0`, `Primary 3`,
`Stage0` — is unmemorable, and unmemorable names are why doctrine gets ignored. Every
identifier in this build is a phrase you can say out loud.

**`GEM` is not a domain term.** `BMS_DDC_GEM_v3.2.docx` is titled *"Senior Estimator
System Prompt — Complete Instructions"*: it is a Gemini *Gem*, a tooling artifact
whose name leaked into the vocabulary. It becomes the **Estimator Playbook** — the
authority on verbs, ownership and phrasing.

| Was | Becomes |
|---|---|
| `R01`–`R43` | kebab-case slugs that *are* the name, e.g. `terminal-unit-ddc-ships-to-factory` (was R36), `valves-are-furnished-and-wired` (was R06), `sequence-beats-boilerplate-exclusion` (was R23) |
| Package A | **factory-integrated** — manufacturer's controls, we wire and map |
| Package B | **factory-plus-field** — as above, plus field dampers and sensors |
| Package C | **field-ddc-air-side** — our DDC, our sensors, start/stop, speed |
| Package D | **terminal-unit-factory-ddc** — controller shipped to the box factory |
| Package E | **unitary-heat-pump** |
| Package F | **hydronic-plant** |
| Package G | **existing-system-tie-in** |
| Package H | **data-centre-integration** |
| `FE`, `fe_mode` | **front end**, `front_end_mode`: `new-system` \| `extend-existing` |
| `GEMS` | **Estimator Playbook** |
| `G0`, `G_VISION` | named gates: `every-page-read`, `every-quantity-sourced`, `no-pending-in-client-doc` |
| `Stage0` | **intake** |
| `Primary 3` | name the three files |
| `C1–C6`, `QC-01–10` | folded into named checks |

Terms that appear in the client document stay exactly as they are — *Front End Web
Enabled BMS System*, *Scope of Work*, *ADD ALTERNATE*, *Qty*. Those are house
vocabulary, not jargon.

Every ported rule also carries a one-line plain-English statement. A rule you cannot
restate in a sentence is a rule nobody will apply.

## 4. Architecture

```
  bid package (drawings, specs, diagrams, addenda, RFIs, exhibits)
         |
    +----v-------------------------------------------+
    | Intake — document register                     |
    |   every page registered (text + vision)        |
    |   tag occurrence index                         |
    |   legend and keynote extraction                |
    |   supersession ladder, revision diff           |
    +----+-------------------------------------------+
         |  system bundle: every page concerning AHU-1
         |
    +----v---------+  +---------------+  +----------------------+
    | A. Equipment |  | B. Devices    |  | C. Scope assembly    |
    |   what units |  |   sensors,    |  |   what we furnish,   |
    |   exist      |  |   stats,      |  |   how it is worded,  |
    |              |  |   actuators   |  |   what it costs      |
    +----+---------+  +-------+-------+  +----------+-----------+
         |                    |                     |
         +--------------------+---------------------+
                              |
                    rules derivation  --+
                                        +--> reconciler
                    model derivation  --+      agree        -> CONFIRMED
                                               differ       -> FLAG (both kept)
                                               rules silent -> ASSUMPTION
                              |
                              v
    ScopeLine[]  --+--> Proposal .docx     (docxtpl, AME template)
                   +--> Price Sheet .xlsx  (openpyxl, PriceWorkup template)
                   +--> Evidence Package   (flags, provenance, change log)
```

### The core type

```python
class Evidence:
    sheet: str                 # "M-002"
    locator: str               # "Fan Coil Unit Schedule row 7" | "15985-18" | "Keynote 7"
    quote: str                 # the actual text found, or the symbol matched
    kind: EvidenceKind         # SCHEDULE|PLAN|SYMBOL|RISER|SEQUENCE|DIAGRAM|MATRIX|SPEC|KEYNOTE|DETAIL
    revision: str              # "base" | "Add.1" | "IFC"
    doc_date: date

class Derivation:
    method: RULE | PLAN_COUNT | MODEL | HUMAN   # PLAN_COUNT = symbols or keynotes
    rule: str | None           # "terminal-unit-ddc-ships-to-factory"
    note: str

class Quantity:
    value: int | None          # None = PENDING. Never a silent 1.
    category: Category         # CONFIRMED|DISCREPANCY|EXTRA|MISSING|ORPHANED|CONFLICT|EXISTING
    confidence: float
    evidence: list[Evidence]   # non-empty, or the build fails
    derivations: list[Derivation]
    alternatives: list[Quantity]   # on disagreement the loser is kept, not discarded
```

### Invariants

Enforced by tests, not convention. Each closes a failure observed in the previous
build.

**I1 — One list, two documents.** The proposal and the price sheet are renderings of
the same `ScopeLine[]`. A line cannot exist in one and not the other. `Price Sheet 1`
already mirrors the scope one row per line; this makes that structural.

**I2 — No number without provenance.** Empty `evidence` fails the build. This is
"never invent", made mechanical.

**I3 — "I don't know" is representable and unrenderable.** `value: None` is legal in
the model and illegal in the client document; the renderer raises. This is what makes
*"as required"* impossible — the tool can say *pending*, so it never has to bluff.

**I4 — Boilerplate lives in the template, not in code.** Exclusions, clarifications,
header table, ADD/DEDUCT sections and signature block are authored in the `.docx`.
Code injects only what varies. The 13 dropped exclusions happened because code was
assembling the list; if the template owns it, no code path can drop it.

**I5 — Internal state has no route to the client document.** Confidence, rule names
and flag markers exist only in review artifacts. The client template has no
placeholder for them, so they cannot leak. Not filtered — structurally absent.

**I6 — Wording is selected, never generated.** Scope line text comes from the
approved phrasing bank (§8.4). An item with no approved phrasing is a flag, not an
invitation to write prose.

### The document shell

Issued `26-0352.docx` is 875,713 bytes; the shell is 875,213. The estimator copies the

controllers, terminal-unit controllers by point count, plant controllers by point

Three things follow from its structure:

1. **It is also a device selection guide.** Rows carry notes such as *"Standard to use

2. **Its line names are close to scope line names.** *Space Temperature / CO2 Sensor*

3. **Incomplete rows are flags, not zeros.** Several entries are marked *"Need review
   from Engg Team"* or *"Need Part # & pricing"*, and the plant-panel block is marked
   incomplete. A scope line whose price is missing must surface as
   `PRICE-PENDING`, never silently price at nothing.

## 7. Intake — document register and system bundle

### 7.1 Recall is deterministic; judgement is not

Reasoning over a bundle of 10–30 pages about one system is reliable. Guaranteeing that
every relevant page was found across a 1,235-PDF package (26-0328) is not, and it
fails silently — nobody knows which page was missed.

So recall never depends on the model:

1. **Page register** — every page of every document, text layer plus vision where
   there is no text layer. A page that could not be read is a hard blocker.
2. **Tag occurrence index** — every occurrence of every equipment tag, located.
3. **Legend and keynote extraction** — the controls symbol legend on each drawing set
   (symbol → device type), and the keynote list on each sheet (number → note text).
   §8.2 counts against both.
4. **System bundle** — "everything about AHU-1" becomes a query, not a search.

This mirrors the manual method — flip through everything, find every page mentioning
the unit — with a guarantee attached.

**Honest limit:** index recall is bounded by text extraction. If vision misses a tag on
a scanned sheet, the index misses it. The `every-page-read` gate stays hard.

### 7.2 Alias resolution

`AHU-1` / `AHU–1` (en dash) / `AHU 1` / `AHU#1` / `Air Handling Unit No. 1` are one
system. `AHU-1` must never match `AHU-10`. Whole-token matching against an alias table,
with the negative cases as test fixtures.

### 7.3 Document authority ladder

| Tier | Documents | Behaviour |
|---|---|---|
| 1 | Mechanical drawings — plans, schedules, details, control diagrams | Primary; establishes scope |
| 2 | Mechanical specs | Primary; establishes requirements and ownership |
| 3 | Addenda / bulletins | **Supersede** tiers 1–2 for the sheets they reissue, by date |
| 4 | RFIs, exhibits | **Additive** — novel scope is added and cited; restatement is ignored |

### 7.4 Supersession — latest date wins, scoped per sheet

**Rule: the latest-dated document wins.** Confirmed practice.

**Scope: per sheet, not per document.** An addendum that reissues M-201 and M-202 says
nothing about VAV-3 on M-301. Applied document-wide, "not mentioned = removed" would
strip most of a job's scope every time an addendum touches two sheets.

```
Addendum 1 (Jan 10) reissues M-201, M-202, spec 230900

  AHU-1 on M-201  -> reissued sheet governs.
                     CO2 absent from new M-201 = REMOVED   [Add.1, M-201 r2]
  VAV-3 on M-301  -> not reissued. Base stands. No change.
```

The reissued sheet list comes from the addendum's drawing list or transmittal,
cross-checked against title-block revision number and date. Spec sections supersede the
same way.

### 7.5 Revision diff

A reissued sheet is a **diff against its predecessor**, not a replacement. Estimator
practice is to compare old and new side by side, use revision clouds to find what
changed, and record *every* change — not only the one being looked for.

- **Text-layer diff** — tags added/removed, schedule rows changed, notes edited.
  Reliable, and it catches most controls-relevant change.
- **Revision clouds** — locate the change and make a clean citation. Vector clouds are
  findable geometrically; raster clouds on scanned sheets need vision; some engineers
  use triangles or deltas. A hint, never the sole authority — the text diff runs
  regardless.
- **Title block** — revision number and date; anchors ordering.

Whole sheet clouded → full re-review of that sheet, flagged as such.

**Deliverable:** the change log is a tab in the Evidence Package.

> Addendum 1 — 14 changes across M-201, M-202, 230900
> 3 affect controls scope · 9 informational · 2 need review
> each with sheet, what changed, old value, new value, action taken

**Will not be caught:** purely geometric change with no text signal — a duct rerouted,
a unit moved. A whole-sheet-clouded case always escalates to full review rather than
trusting the diff.

## 8. The three chains

The previous build ran equipment and devices as one pass, which is why it wrote
*"as required"* when the schedule ran out. They are different problems with different
evidence and different failure modes.

### 8.1 Chain A — what units exist

- Schedule is primary (`Quantity rules.txt` Rule 1)
- Plans locate and verify; risers and control diagrams cross-check (Rule 2)
- Every item lands in exactly one Rule 3 category; nothing is unclassified
- Rule 7 (duplicate tag), Rule 8 (typical/type-only schedule) and Rule 9 (paired
  systems) port verbatim, with their worked examples as test fixtures

**Typical-floor expansion.** A sheet marked *typical floors 3 thru 14* multiplies its
contents. The multiplier is **the count of actual floors in the building's floor
list**, not `last - first + 1` — a building that omits floor 13 breaks the arithmetic.
It renders as a cited line:

```
Typical plan M-301 -> floors 3-14. Floor list (A-001): 12 floors.
Multiplier = 12.  [CONFIRMED — A-001]
```

**Missing-tag inference.** An untagged unit adjacent to a tagged run can often be
identified from its neighbours. Permitted, never silent: category `ORPHANED` or
`DISCREPANCY`, with the inference stated.

### 8.2 Chain B — device takeoff

Schedules give equipment. They do not give sensors, thermostats, damper actuators or
controllers — and those are the scope. This chain counts them, in this source order:

| Priority | Source | Confidence |
|---|---|---|
| 1 | **Plan evidence** — device symbols matched against the legend, and device keynotes placed on the sheet | highest; it is a count, not a derivation |
| 2 | **Point list / control matrix** — spec gives points per unit | high |
| 3 | **Sequence of operation** — implies which points exist | medium |
| 4 | **Standard package** — the AME default for that equipment class, from the price book's selection notes and ASHRAE Guideline 36 | assumption; always flagged |

**The delivery model decides which source exists.** Confirmed practice: devices are
counted from the plans whenever they are drawn there, as symbols or as keynotes. On
design-bid-build the controls contractor designs the layout, so the plans may show
equipment but no devices, and quantity must be derived from tiers 2–4. The tool detects
which world a job is in and says so:

> `No device symbols or device keynotes found on plan sheets (28 sheets searched,`
> `legend absent). Device quantities derived from sequence and standard packages — see flags.`

**Symbols.** Extract the controls legend, which gives symbol → device type.
Template-match each legend symbol across plan sheets at drawing scale, with the match
scored and the hit located. Every counted device carries a `SYMBOL` evidence record
naming the sheet and position, so a disputed count can be pointed at.

**Keynotes.** Devices are often not drawn as symbols but called out with a keynote — a
number in a hexagon or circle, placed at the location, pointing to the sheet's keynote
list. Only 7 of 279 issued proposals cite a keynote explicitly, but that undercounts
use: estimators read a keynote and write the line without citing it. Where they do cite
one, it is carrying something large:

| Job | Issued line |
|---|---|
| 26-0190 | Space Static Pressure Sensor – (Qty. 24 Total) – as per IC00-02 Keynote #14 |
| 26-0328 | Data Hall to Corridor Differential Pressure Sensor – Qty. 20 (Keynote 9) |
| 26-0267 | Qty (182) Existing FTR-# (Scope as per Demo Plan Key notes) |
| 25-0671 | Sump Box Leak Sensor; Wired by Others – as per key note #27 |
| 25-0749 | *All scope with Fire Alarm by Others. Key Note #23 on M-110.07 |
| 25-0726 | EF-5 – Scope as per Keynote #3 on M-404 |

A keynote therefore carries more than a count. Its text gives the device type, and
often the ownership, an exclusion, or a unit's entire scope. It feeds Chain B with a
count and Chain C with ownership and wording.

*Count* = placements of the callout on the sheet. *Type* = the keynote's text.

Three traps, each flagged rather than guessed:

- **A bare number is everywhere.** A "7" appears in dimensions, grid lines, room numbers
  and sheet references. A placement counts only when the number sits inside a keynote
  shape — hexagon, circle or diamond, per the sheet's convention — and matches an entry
  in that sheet's keynote list. Without the enclosing-shape check, every "7" on the sheet
  becomes a sensor.
- **"TYP." multiplies.** A keynote placed once and marked *typical* applies to every
  similar location. Counting the single placement undercounts; the modifier is parsed
  and the multiplier made explicit, the same way typical-floor expansion is (§8.1).
- **Numbering is per sheet.** Keynote 7 on M-101 and keynote 7 on M-102 are different
  notes. Every keynote reference is keyed by sheet, never by number alone.

Every counted keynote placement carries a `KEYNOTE` evidence record naming the sheet,
the keynote number, its text and the placement position.

**Honest limits, stated now rather than discovered later:** symbol sets are not
standardised between engineering firms, which is why the legend is the entry point
rather than a fixed symbol library. Scanned sheets degrade matching. Dense plans
produce overlapping hits. Every one of those is a flag, never a silent number.

### 8.3 The grouping question

Device count is not a function of unit count. From issued 26-0246:

| Block | Units | Thermostats |
|---|---|---|
| CBH-A | 4 | **1** |
| ECUH-## | 43 | **42** |
| Electric Baseboard | 8 | **5** |
| Electric Baseboard | 105 | **0** — interlocked with associated VAV |

Four heaters in one vestibule share one stat; 105 baseboards inside VAV zones need
none. This is exactly why Chain B exists as a counting chain rather than a
multiplication: **when the plan shows one thermostat — as a symbol or a keynote —
serving four heaters, the answer is one, and you get it by counting rather than
reasoning.**

Where nothing exists to count, it falls to tier 4 and becomes a review question with an
honest default:

```
ECUH-## — 43 units, M-101…M-104. No thermostat symbols or keynotes on these sheets.
Schedule and sequence silent.  Default 1:1 -> 42  [ASSUMPTION].  Confirm grouping.
```

The failure to avoid is not getting 42 wrong; it is **silently emitting 43** when the
answer is 1. One is a ten-second decision, the other is a priced error nobody sees.

Over time the corpus supplies priors — *"cabinet heaters in a vestibule grouped to a
single stat in 38 of the last 40 jobs"* — and a prior with evidence beats an invented
rule. That is the mechanism by which the tool stops needing per-job patching.

### 8.4 Chain C — scope assembly

| Layer | Source |
|---|---|
| Which equipment package | job class + equipment type + evidence — the eight packages named in §3 |
| Which lines in the package | sequence, control diagram, point matrix, spec; Guideline 36 minimums as the floor |
| What quantity per line | Chain B |
| Which device is selected | price book selection notes — e.g. space temperature sensor standard for all terminal units |
| What wording | the 691-line approved phrasing bank (I6) |
| What it costs | price book material price + labour book hours |

`2024_Template.docx` yields the phrasing bank. Unmatched items raise *"no approved
wording for this scope item"* — which is also how the bank grows, deliberately, with
review.

## 9. Reconciler and review queue

Rules and model derive scope **independently** from the same bundle. Where Chain B
counted symbols or keynotes, that count is a third voice.

| Outcome | Category | Behaviour |
|---|---|---|
| Sources agree | `CONFIRMED` | high confidence; renders |
| Sources differ | `DISCREPANCY` | every answer and citation goes to the queue; renders only after resolution |
| Rules silent, model proposed | `ASSUMPTION` | renders, with the assumption logged and cited |
| Nothing establishes it | `PENDING` | cannot render (I3) |
| Price book has no entry | `PRICE-PENDING` | scope line renders; price cell flags |

This is `Quantity rules.txt` Rule 2 raised one level: cross-check the schedule against
every supporting sheet that exists, and confirm nothing until they agree — applied from
sheet-vs-sheet to method-vs-method.

Confidence derives from **evidence agreement**, never from a model's self-assessment. A
model reporting `0.85` about its own output is not a number that belongs in a priced
document.

## 10. The harness

Without this, every change is a guess and "don't patch it per job" is unmeasurable.

Replay N of the 268 paired jobs; generate and diff against the issued proposal.

| Dimension | Measure |
|---|---|
| Equipment blocks | recall / precision — a missing block is the worst failure |
| Block quantities | agreement on the `Qty (N)` header |
| **Device lines** | recall / precision — the Occupancy ×21 class of error |
| **Device quantities** | agreement, split by source tier so symbol counting and keynote counting are each scored on their own |
| Wording | drawn from the approved bank; matches issued text |
| Price | line total vs. the filled workup, on the 61 jobs that have one |
| Boilerplate integrity | **binary, must be 100%** — every exclusion and clarification present |
| Structural integrity | **binary, must be 100%** — styles, header table, zero internal markers |

**The human is not always right.** Every delta is classified `new-better` /
`new-worse` / `neutral`, with sampled human adjudication. The release bar is **no
`new-worse` deltas**, not "higher score".

### On Brick Schema

It supplies the **equipment class backbone** — the registry whose absence produced
`EWH EWH`, `FTR-PERIM`, `FSD-EXIST` and `VAV-21-01..12`. With it, an instance is
`{class: VAV, tags: [VAV-21-01 … VAV-21-12], display: "VAV-21-01 thru 12"}` and
rendering is a lookup rather than string concatenation.

It is **not** a scope vocabulary. Brick was built for live building metadata and has no
notion of *"Furnish BMS Communication Wiring to Factory Controls"* or *"24V Transformer
by Unit Mfr."* Those come from the phrasing bank and the price book. Do not force scope
lines into Brick points.

**Open:** depend on the package (rdflib + SHACL reasoning) or vendor the class hierarchy
as a static table. Leaning static — a naming registry does not need a reasoner.

**Alternative considered:** Project Haystack (`phable` 0.1.29, MIT). Tag-based rather
than class-based and arguably closer to integrator vocabulary, but its tooling targets
live Haystack servers. `hszinc` is dead (2023). Brick preferred.

**ASHRAE 223P** — the eventual successor merging Brick and Haystack thinking — is still
a public review draft, publication expected FY26, second review pending. Too immature to
build on.

**ASHRAE Guideline 36** is a standard, not a library. It supplies the minimum point list
per equipment class, which is what makes *"as required"* unnecessary: either something
establishes the point, or the Guideline 36 default applies and is flagged with a
citation.

**There is no HVAC controls estimating library.** The domain knowledge lives in
`Brain/`, in the price book, in the 286 issued proposals, and in the estimators. The
stack's job is to give it somewhere solid to live.

## 12. Build order

Five milestones, each independently useful, each ending in something runnable.

**M1 — Render truthfully.** Convert the shell into a `docxtpl` template; fill it from a
hand-written `ScopeLine[]` fixture for one real job. Add the price sheet fill with
formula preservation, and the price book join. Enforce I1, I4, I5. No extraction at all.

*Why first:* it is the entire "presentable" half, it is deterministic, and it makes every
later milestone's output immediately inspectable. Done when a fixture round-trips to a
document that is byte-plausible against issued 26-0352.

**M2 — The harness.** Score generated output against issued proposals across the 268
paired jobs. Runs against M1's renderer with fixtures, so the scoring dimensions are
proven before anything depends on them.

*Why second:* it converts "don't patch it per job" from an aspiration into a number.

**M3 — Intake.** Page register, tag occurrence index, alias resolution, legend
extraction, supersession ladder, revision diff and the change log.

**M4 — Chain A.** Equipment inventory: schedule extraction, plan locate, typical-floor
expansion, the Rule 1–9 cross-check, Rule 3 categorisation.

**M5 — Chain B and C.** Device takeoff by symbol and keynote count with the tiered
fallback, package selection, phrasing bank, dual derivation, review queue.

*Why last:* it is the largest and the most judgement-heavy, and it is the one that most
needs a scoreboard that already exists before work starts.

The order is deliberate: **deterministic, testable work first; judgement-heavy work
last, against a scoreboard that already exists.**

## 14. Open questions

1. **Labour book.** Tech hours per scope line are still to be supplied. The price book
   covers material only. Blocks the hours column of the price sheet, not the proposal.
2. **Price book join.** Scope line names map closely to price book rows but not exactly.
   Needs validating against the 61 filled workups, and the gaps listed.
3. **House style.** 26-0246 uses `Qty (N) Equipment TAG` with `– (Qty. N Total)`;
   26-0352 uses `(xN) TAG` with `- (xN)`. Different estimators. Need one canonical form,
   or a per-estimator switch.
4. **Guideline 36 validation.** Minimum point lists need checking against AME practice
   before they become defaults — it is a design standard, not a bid standard.
5. **Plan-evidence coverage.** Confirmed practice: devices are counted from plans when
   drawn, as symbols or keynotes. The share of jobs where they are drawn is unknown, and
   is **measured by the harness** rather than estimated — it decides how much weight
   tier 1 carries versus tiers 2–4 (§8.2).
6. **Brick dependency vs. vendored table** (§11).
7. **Job-class coverage.** The six classes in `decision_model_v2` came from 7 jobs.
   Whether they cover the 268 needs checking.

**Answered:** roughly 10% of packages arrive as scanned image PDFs (§6).
