# Estimator AI — Design

**Date:** 2026-09-24
**Status:** Design approved in conversation; awaiting spec review
**Supersedes:** `D:\Estimation Assistant` (read-only reference from here on)
**Reference corpus:** `D:\AME Estimation` (read-only)

---

## 1. What this is

A tool that reads an HVAC/BMS controls bid package — mechanical drawings, specs,
control diagrams, addenda, RFIs, exhibits — and produces two deliverables that an
AME estimator can issue after a short, structured review:

1. **Proposal** (`.docx`) — the client-facing scope of work
2. **Price Sheet** (`.xlsx`) — the same scope, priced

Plus a third artifact that is not optional, and is the reason the first two can be
trusted:

3. **Evidence Package** (`.xlsx`) — every quantity's provenance, every flag, every
   discrepancy, every assumption, every revision change

### Core value

**A scope you can defend, line by line.** If a number in the proposal cannot be
traced to a sheet, a spec paragraph, or a named assumption, the tool has failed —
regardless of whether the number happens to be right.

### Success criterion

The estimator's job changes from *writing the scope* to *resolving a short list of
flagged decisions*. The measure is the length of that list and the rate at which its
defaults are accepted, tracked against the reference corpus (§5).

nothing would have enforced it.

The work is turning existing doctrine into data structures and tests.

## 3. Architecture

```
  bid package (drawings, specs, diagrams, addenda, RFIs, exhibits)
         |
    +----v------------------------------------------+
    | Chain 0 — document register                   |
    |   every page registered (text + vision)       |
    |   tag occurrence index                        |
    |   supersession ladder                         |
    |   revision diff                               |
    +----+------------------------------------------+
         |  system bundle: all pages concerning AHU-1
    +----+----+
    | Chain A |  what units exist
    +---------+
    | Chain B |  what we furnish for each unit
    +----+----+
         |
         |   rules derivation  --+
         |                       +--> reconciler
         |   model derivation  --+       agree        -> CONFIRMED
         |                               differ       -> FLAG (both kept)
         |                               rules silent -> ASSUMPTION
         v
    ScopeLine[]  --+--> Proposal .docx     (docxtpl, AME template)
                   +--> Price Sheet .xlsx  (openpyxl, PriceWorkup template)
                   +--> Evidence Package   (flags, provenance, change log)
```

### The core type

```python
class Evidence:
    sheet: str                 # "M-002"
    locator: str               # "Fan Coil Unit Schedule row 7" | "15985-18" | "Keynote 7"
    quote: str                 # the actual text found
    kind: EvidenceKind         # SCHEDULE|PLAN|RISER|SEQUENCE|DIAGRAM|MATRIX|SPEC|KEYNOTE|DETAIL
    revision: str              # "base" | "Add.1" | "IFC"
    doc_date: date

class Derivation:
    method: RULE | MODEL | HUMAN
    rule_id: str | None        # "R36" | "Quantity Rule 8"
    note: str

class Quantity:
    value: int | None          # None = PENDING. Never a silent 1.
    category: Category         # CONFIRMED|DISCREPANCY|EXTRA|MISSING|ORPHANED|CONFLICT|EXISTING
    confidence: float
    evidence: list[Evidence]   # non-empty, or the build fails
    derivations: list[Derivation]
    alternatives: list[Quantity]   # on disagreement the loser is kept, not discarded
```

### Invariants

Enforced by tests, not convention. Each one closes a failure observed in the previous
build.

**I1 — One list, two documents.** The proposal and the price sheet are renderings of
the same `ScopeLine[]`. A line cannot exist in one and not the other. `Price Sheet 1`
already mirrors the SOW one row per line; this makes that structural.

**I2 — No number without provenance.** Empty `evidence` fails the build. This is
`ESTIMATOR_DOCTRINE`'s "never invent", made mechanical.

**I3 — "I don't know" is representable and unrenderable.** `value: None` is legal in
the model and illegal in the client document; the renderer raises. This is what makes
`"as required"` impossible — the tool can say *pending*, so it never has to bluff.

**I4 — Boilerplate lives in the template, not in code.** Exclusions, clarifications,
header table, ADD/DEDUCT sections and signature block are authored in the `.docx`.
Code injects only what varies. The 13 dropped exclusions happened because code was
assembling the list; if the template owns it, no code path can drop it.

**I5 — Internal state has no route to the client document.** Confidence, rule IDs and
flag markers exist only in review artifacts. The client template has no placeholder
for them, so they cannot leak. Not filtered — structurally absent.

**I6 — Wording is selected, never generated.** Scope line text comes from the approved
phrasing bank (§7.4). An item with no approved phrasing is a flag, not an invitation
to write prose.

## 4. The two document assets

Confirmed by inspection. They are different things with different jobs.

| File | Role | Shape |
|---|---|---|
| `AME_nordomatic Proposal Template.docx` | **Document shell** | 87 paragraphs, 1 header table, `Heading 1`/`PR1`/`PR2`/`PR3`/`List Paragraph`, full exclusions + clarifications + ADD/DEDUCT + Base Price + signature |
| `Brain/2024_Template.docx` | **Phrasing bank** | 810 paragraphs, zero tables, 691 approved `PR2` scope lines, no document furniture |

Evidence they are used exactly this way: issued `26-0352.docx` is 875,713 bytes; the
shell is 875,213. The estimator copies the shell and types scope into it.

`proposal template.docx` is a stale variant (2024 dates, 60-day validity, no tariff
clause). Not canonical.

### Template conversion

The shell becomes a `docxtpl` template. Two things in it are conditionals, not
clutter, and must survive conversion:

- **Two front-end openings**, separated by a literal `OR` line — new BMS vs. extension
  of an existing district-wide BMS. Selected from spec evidence, with a citation.
  Where the spec is silent this is a review question, never a default: picking the
  wrong FE block is a five-figure error in either direction.
- **`IT Infrastructure – By AME or by Others?`** with `Network Switches / Panels /
  Fiber – Ethernet`. A decision point; becomes a review question.

Genuinely removable: the duplicated exclusion (`"Any demolition work not mentioned."`
and `"Any demolition work not specifically mentioned"` are both present) and the stale
template date.

## 6. Chain 0 — document register and system bundle

### 6.1 Recall is deterministic; judgement is not

Reasoning over a bundle of 10–30 pages about one system is reliable. Guaranteeing that
every relevant page was found across a 1,235-PDF package (26-0328) is not, and it
fails silently — nobody knows which page was missed.

So recall never depends on the model:

1. **Page register** — every page of every document, text layer plus vision where
   there is no text layer. A page that could not be read is a hard blocker, not a
   warning.
2. **Tag occurrence index** — every occurrence of every equipment tag, located.
3. **System bundle** — "everything about AHU-1" becomes a query, not a search.

This mirrors the manual method (flip through everything, find every page mentioning
the unit) with a guarantee attached.

**Honest limit:** index recall is bounded by text extraction. If vision misses a tag
on a scanned sheet, the index misses it. The `vision_required` gate stays hard.

### 6.2 Alias resolution

`AHU-1` / `AHU–1` (en dash) / `AHU 1` / `AHU#1` / `Air Handling Unit No. 1` are one
system. `AHU-1` must never match `AHU-10`. Whole-token matching with an alias table;
port the approach from the Takeoff Pro backend rather than re-deriving it.

### 6.3 Document authority ladder

| Tier | Documents | Behaviour |
|---|---|---|
| 1 | Mechanical drawings — plans, schedules, details, control diagrams | Primary; establishes scope |
| 2 | Mechanical specs | Primary; establishes requirements and ownership |
| 3 | Addenda / bulletins | **Supersede** tiers 1–2 for the sheets they reissue, by date |
| 4 | RFIs, exhibits | **Additive** — novel scope is added and cited; restatement is ignored |

### 6.4 Supersession — latest date wins, scoped per sheet

**Rule: the latest-dated document wins.** Confirmed practice.

**Scope: per sheet, not per document.** An addendum that reissues M-201 and M-202 says
nothing about VAV-3 on M-301. Applied document-wide, "not mentioned = removed" would
strip most of a job's scope every time an addendum touches two sheets.

```
Addendum 1 (Jan 10) reissues M-201, M-202, spec 230900

  AHU-1 on M-201  -> reissued sheet governs.
                     CO2 absent from new M-201 = REMOVED   [Add.1, M-201 r2]
  VAV-3 on M-301  -> not reissued. Base stands. No change.
```

The reissued sheet list comes from the addendum's drawing list or transmittal,
cross-checked against title-block revision number and date. Spec sections supersede
the same way.

### 6.5 Revision diff

A reissued sheet is a **diff against its predecessor**, not a replacement. Estimator
practice is to compare old and new side by side, use revision clouds to find what
changed, and record *every* change — not only the one being looked for.

Three signals, mutually reinforcing:

- **Text-layer diff** — tags added/removed, schedule rows changed, notes edited.
  Reliable, and it catches most controls-relevant change, because controls scope is
  driven by things that have text.
- **Revision clouds** — locate the change and make a clean citation. Vector clouds are
  findable geometrically; raster clouds on scanned sheets need vision; some engineers
  use triangles or deltas instead. A hint, never the sole authority — the text diff
  runs regardless.
- **Title block** — revision number and date; anchors ordering.

Whole sheet clouded → full re-review of that sheet, flagged as such.

**Deliverable:** the change log is a tab in the Evidence Package, not an internal
artifact.

> Addendum 1 — 14 changes across M-201, M-202, 230900
> 3 affect controls scope · 9 informational · 2 need review
> each with sheet, what changed, old value, new value, action taken

**Will not be caught:** purely geometric change with no text signal — a duct rerouted,
a unit moved. Rarely changes controls scope, but a whole-sheet-clouded case always
escalates to full review rather than trusting the diff.

## 7. Chains A and B

The previous build conflated these, which is why it emitted `"as required"` when the
schedule ran out. They have different evidence, different confidence and different
failure modes.

### 7.1 Chain A — what units exist

- Schedule is primary (`Quantity rules.txt` Rule 1)
- Plans locate and verify; risers and control diagrams cross-check (Rule 2)
- Every item lands in exactly one Rule 3 category; nothing is unclassified
- Rule 7 (duplicate tag), Rule 8 (typical/type-only schedule) and Rule 9 (paired
  systems) port verbatim, with their worked examples as test cases

**Typical-floor expansion.** A sheet marked *typical floors 3 thru 14* multiplies its
contents. The multiplier is **the count of actual floors in the building's floor
list**, not `last - first + 1` — a building that omits floor 13 breaks the arithmetic.
It renders as a cited line:

```
Typical plan M-301 -> floors 3-14. Floor list (A-001): 12 floors.
Multiplier = 12.  [CONFIRMED — A-001]
```

**Missing-tag inference.** An untagged unit adjacent to a tagged run can often be
identified from its neighbours. Permitted, but never silent: category `ORPHANED` or
`DISCREPANCY`, with the inference stated.

### 7.2 Chain B — what we furnish for each unit

Four layers:

| Layer | Source |
|---|---|
| Which package (A–H) | job class + equipment type + evidence — `decision_model_v2` §3 |
| Which lines in the package | sequence, control diagram, point matrix, spec; **ASHRAE Guideline 36 minimums as the floor** |
| What quantity per line | 1:1 with units, a separate locate, or a **grouping judgement** |
| What wording | the 691-line approved phrasing bank (I6) |

### 7.3 The grouping problem

Scope quantity is not a function of unit count. From issued 26-0246:

| Block | Units | Thermostats |
|---|---|---|
| CBH-A | 4 | **1** |
| ECUH-## | 43 | **42** |
| Electric Baseboard | 8 | **5** |
| Electric Baseboard | 105 | **0** — interlocked with associated VAV |

Thermostat count is a function of **zoning** — how many independently controlled
spaces the units serve — read off a plan. Four CBH-A in one vestibule share a stat;
105 baseboards inside VAV zones need none.

Solving this automatically requires room boundaries and device locations: a geometry
problem, and out of scope for v1.

**v1 behaviour** — a first-class review question with an honest default:

```
ECUH-## — 43 units, M-101…M-104.
Thermostat count: schedule and sequence silent.
Default 1:1 -> 42  [ASSUMPTION — no evidence].  Confirm grouping.
```

The failure to avoid is not getting 42 wrong; it is **silently emitting 43** when the
answer is 1. One is a ten-second decision, the other is a priced error nobody sees.

**v2 path** — mine the corpus for priors: *"CBH in a vestibule grouped to a single stat
in 38 of the last 40 jobs."* A learned prior with evidence beats an invented rule, and
it is the mechanism by which the tool stops needing per-job patching.

### 7.4 Phrasing bank

`2024_Template.docx` yields 691 approved `PR2` lines. Scope text is selected from this
bank (I6). Unmatched items raise *"no approved wording for this scope item"* — which is
also how the bank grows, deliberately, with review.

## 8. Reconciler and review queue

Rules and model derive scope **independently** from the same bundle.

| Outcome | Category | Behaviour |
|---|---|---|
| Both agree | `CONFIRMED` | high confidence; renders |
| They differ | `DISCREPANCY` | both answers and both citations go to the queue; renders only after resolution |
| Rules silent, model proposed | `ASSUMPTION` | renders, with the assumption logged and cited |
| Neither can establish it | `PENDING` | cannot render (I3) |

This is `Quantity rules.txt` Rule 2 raised one level: cross-check the schedule against
every supporting sheet that exists, and confirm nothing until they agree — applied from
sheet-vs-sheet to method-vs-method.

Confidence is derived from **evidence agreement**, never from a model's
self-assessment. A model reporting `0.85` about its own output is not a number that
belongs in a priced document.

## 9. The harness

Without this, every change is a guess and "don't patch it per job" is unmeasurable.

Replay N of the 268 paired jobs. For each, generate and diff against the issued
proposal:

| Dimension | Measure |
|---|---|
| Equipment blocks | recall / precision — a missing block is the worst failure |
| Block quantities | agreement on the `Qty (N)` header |
| Scope lines within matched blocks | recall / precision |
| Scope line quantities | agreement — the Occupancy ×21 class of error |
| Wording | drawn from the approved bank; matches issued text |
| Boilerplate integrity | **binary, must be 100%** — every exclusion and clarification present |
| Structural integrity | **binary, must be 100%** — styles, header table, zero internal markers |

Money-weighted scoring is possible on the 61 jobs with a filled price workup, since
those carry tech hours and unit prices per line.

**The human is not always right.** Every delta is classified `new-better` /
`new-worse` / `neutral`, with sampled human adjudication. The release bar is **no
`new-worse` deltas**, not "higher score".

## 10. Stack

Versions verified on PyPI, 2026-09-24.

| Need | Choice | Version | Note |
|---|---|---|---|
| Domain model / validation | `pydantic` | 2.13.5 | MIT. Enforces §3 types at every boundary |
| PDF parse, text layer, render | `pymupdf` | 1.28.2 | **AGPL-3.0-or-commercial.** Text extraction, page register, revision diff. Internal use inside one legal entity is not conveying, so fine as an internal tool; distributing outside Nordomatic requires an Artifex licence |
| Proposal render | `docxtpl` | 0.20.2 | **LGPL-2.1-only.** Jinja2 inside a `.docx`; preserves styles, header table, numbering. Fine for an internal tool; a conscious licence call |
| …under it | `python-docx` | 1.2.0 | MIT |
| Price sheet fill | `openpyxl` | 3.1.5 | MIT. **Load `data_only=False`** — `data_only=True` loses every formula on save, and the Summary tab is entirely formulas |
| Equipment vocabulary | Brick Schema | `brickschema` 0.7.9 | BSD-3. Class backbone only |

### On Brick Schema

It supplies the **equipment class backbone** — the registry whose absence produced
`EWH EWH`, `FTR-PERIM`, `FSD-EXIST` and `VAV-21-01..12`. With it, an instance is
`{class: VAV, tags: [VAV-21-01 … VAV-21-12], display: "VAV-21-01 thru 12"}` and
rendering is a lookup rather than string concatenation.

It is **not** a scope vocabulary. Brick was built for live building metadata and has no
notion of *"Furnish BMS Communication Wiring to Factory Controls"* or *"24V Transformer
by Unit Mfr."* Those come from the AME scope vocabulary, extended from the phrasing
bank. Do not force SOW lines into Brick points.

**Open:** whether to depend on the package (rdflib + SHACL reasoning) or vendor the
class hierarchy as a static table. Leaning static — a naming registry does not need a
reasoner.

**Alternative considered:** Project Haystack (`phable` 0.1.29, MIT). Tag-based rather
than class-based, and arguably closer to integrator vocabulary, but its tooling targets
live Haystack servers. `hszinc` is dead (2023). Brick preferred.

**ASHRAE 223P** — the eventual successor merging Brick and Haystack thinking — is still
a public review draft, with publication expected FY26 and a second public review
pending. Too immature to build on. Revisit after publication.

**ASHRAE Guideline 36** is a standard, not a library. It supplies the minimum point list
per equipment class, which is what makes `"as required"` unnecessary: either the sequence
establishes the point, or the G36 default applies and is flagged as an assumption with a
citation.

**There is no HVAC controls estimating library.** The domain knowledge lives in
`Brain/`, in the 286 issued proposals, and in the estimators. The stack's job is to give
it somewhere solid to live.

## 11. Build order

This design describes a product, not a single implementation plan. It decomposes into
five milestones, each independently useful and each ending in something runnable.

**M1 — Render truthfully.** Convert the AME shell into a `docxtpl` template; fill it
from a hand-written `ScopeLine[]` fixture for one real job. Add the price sheet fill
with formula preservation. Enforce I1, I4, I5. No extraction at all.

*Why first:* it is the entire "presentable" half of the ask, it is deterministic, and
it makes every later milestone's output immediately inspectable. Done when a fixture
round-trips to a document that is byte-plausible against the issued 26-0352 — correct
styles, header table, complete boilerplate, no internal markers.

**M2 — The harness.** Score generated output against issued proposals across the 268
paired jobs. Runs against M1's renderer with fixtures at first, so the scoring
dimensions are proven before anything depends on them.

*Why second:* it converts "don't patch it per job" from an aspiration into a number.
Every milestone after this is measured.

**M3 — Chain 0.** Page register, tag occurrence index, alias resolution, supersession
ladder, revision diff and the change log.

*Why third:* Chains A and B are queries against this. Building them first would mean
building them twice.

**M4 — Chain A.** Equipment inventory: schedule extraction, plan locate, typical-floor
expansion, the Rule 1–9 cross-check, Rule 3 categorisation. Harness measures block
recall and quantity agreement.

**M5 — Chain B and the reconciler.** Package selection, line derivation, the phrasing
bank, dual derivation and the review queue. This is where the remaining accuracy lives
and where the harness earns its keep.

The order is deliberate: **the deterministic, testable work comes first, and the
judgement-heavy work lands last, against a scoreboard that already exists.**

## 13. Open questions

1. **Pricing inputs.** The price sheet needs tech hours and unit price per scope line.
   The 61 filled workups are a source, but whether a maintained rate table exists — and
   who owns it — is unknown. Blocks the price sheet, not the proposal.
2. **House style.** 26-0246 uses `Qty (N) Equipment TAG` with `– (Qty. N Total)`;
   26-0352 uses `(xN) TAG` with `- (xN)`. Different estimators. Need one canonical form,
   or a per-estimator switch.
3. **Scanned-PDF share.** What fraction of real jobs arrive as image-only PDFs
   determines how much vision sits on the critical path.
4. **G36 validation.** The minimum point lists need checking against AME practice before
   they become defaults — G36 is a design standard, not a bid standard.
5. **Brick dependency vs. vendored table** (§10).
6. **Job-class coverage.** `decision_model_v2` §1 lists six classes derived from 7 jobs.
   Whether those cover the 268 needs checking.

## 14. Rules of engagement

- `D:\Estimation Assistant` and `D:\AME Estimation` are **read-only**. No writes, no
  builds, no test runs against either.
- Every quantity carries provenance, or the build fails.
- A hardening claim without a failing test does not count — this is recorded twice in
  the previous build's audit history.
- Nothing is pushed without a milestone.
